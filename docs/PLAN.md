# File Share — план дальнейшей работы

## Уточнение архитектуры по схеме задания

RabbitMQ выполняет роль шины D1. Отдельную шину поверх него не создаём.

У upload (S2) и download (S3) общее хранилище B2: содержимое файлов, атрибуты и история скачиваний. Для него используем уже работающую upload_db; существующие данные не переносим и не удаляем. Отдельную download_db и репликацию содержимого через RabbitMQ не делаем.

В PDF есть несогласованность: общий пункт «у каждого сервиса своя БД» и общая B2 в конкретной файловой схеме. После уточнения пользователем рабочей основой принимаем конкретную схему с общей B2; эту неоднозначность следует отметить преподавателю, а не молча выдавать альтернативную архитектуру за требование.

Авторизация использует B1 (auth_db), каталог — B4 (своя catalog_db). S1, S2 и S3 публикуют события об изменениях через RabbitMQ в S4. Пользовательские команды по-прежнему идут через HTTP-шлюз.

## Текущее состояние

Реализованы:
- Сервис авторизации: регистрация, вход, проверка хеша пароля, выпуск JWT.
- Сохранение входа в HttpOnly-cookie, восстановление состояния страницы и выход. JWT действует 15 минут; автоматического обновления и серверного отзыва токенов пока нет.
- Шлюз: единая точка HTTP-доступа, пересылка запросов авторизации и загрузки, проверка токена.
- Общий пакет httpauth: независимая проверка токена в разных сервисах.
- Сервис upload: приём одного файла, определение владельца по проверенному токену, ограничение размера, сохранение метаданных и содержимого в PostgreSQL.
- Отдельные контейнеры и тома auth-db и upload-db.
- Простая браузерная страница регистрации, входа, выхода и загрузки.

Пользователь успешно загрузил текстовый файл через браузер и посмотрел его данные/начало текста в БД. Это подтверждает рабочую цепочку приёма и сохранения, но не завершает всё задание.

Текущий лимит загрузки в коде — 1 000 000 байт. В дальнейшем используем одно и то же значение в правилах сервиса, HTTP-ограничениях и подсказках интерфейса. Формат не ограничиваем, содержимое не преобразуем в PDF.

Ещё не реализованы обязательная шина событий, отдельные сервисы скачивания и каталога, удаление файлов, смена имени, статистика, поиск, сортировка и пагинация.

## Принципы продолжения

- Пользователь пишет Go сам; объяснять новые механизмы на текущем коде. Давать законченные небольшие участки, не весь проект сразу.
- Не возвращаться к длинной серии одинаковых учебных тестов. Развивать работающую цепочку, затем проверять связанный набор сценариев.
- Не удалять пользователей, файлы, тома и постоянные ключи ради новой инфраструктуры.
- Не переносить файловые таблицы в auth_db. Только upload и download совместно используют файловую B2; каталог строит собственные данные из событий, а не читает B2 напрямую.
- HTTP остаётся между клиентом, шлюзом и нужным сервисом. Между предметными сервисами — асинхронные события, а не цепочки синхронных HTTP-вызовов.
- Не добавлять Kubernetes, Elasticsearch, отдельный frontend-фреймворк и другие необязательные компоненты.

## 0. Зафиксировать рабочий этап

Перед дальнейшими изменениями сохранить в Git текущую рабочую версию. Проверить, что .env, постоянные закрытые ключи и локальные данные не попадают в коммит. Автоматически коммит не создавался.

Сейчас не нужно выполнять этот пункт немедленно; это начало следующего рабочего отрезка.

## 1. RabbitMQ и первый надёжный поток событий

Цель: загрузка файла должна сообщать об изменении другим сервисам и не терять это сообщение при недоступной шине.

Работы:
- Добавить RabbitMQ в Compose с постоянным томом и локально доступной панелью управления.
- Выбрать и зафиксировать форматы событий: event_id, тип, версия схемы, ID сущности, версия изменения, время, полезные данные.
- Создать очереди и привязки до отправки первых сообщений, в том числе если потребитель ещё не запущен.
- Добавить outbox в общей B2 (нынешняя upload_db): запись файла и исходящего события выполняется одной транзакцией. Для издателей upload и download различать источник записей и обработку их фоновой отправки, чтобы остановка upload не останавливала отправку событий скачивания.
- Добавить фоновую отправку накопленных событий. После восстановления брокера отправка продолжается без повторной загрузки файла пользователем.
- Использовать подтверждения публикации и контроль отсутствующего маршрута; получатель подтверждает сообщение после фиксации своих данных.
- У получателей вести учёт обработанных event_id, чтобы повторная доставка не повторяла изменение.

Рабочий вариант контрактов:
- FileCreated — метаданные нового файла для каталога.
- FileDeleted — информация об удалении для каталога.
- FileDownloaded — информация о скачивании для счётчика и статистики каталога.
- UserRegistered и UserProfileChanged — данные пользователя и изменение отображаемого имени для каталога.

Названия и состав окончательно фиксируем перед реализацией, чтобы разные части проекта не использовали несовместимые события. Содержимое файлов через RabbitMQ не передаём: оно уже доступно upload и download в общей B2. Получатель событий по схеме задания — каталог S4.

Уже загруженные файлы не теряем: нужен однократный перенос их текущего состояния в исходящие события. Аналогично позже синхронизируем существующих пользователей для каталога.

Признак готовности этапа: файл сохраняется, событие наблюдается в очереди; при отключённом брокере оно остаётся в outbox и отправляется после восстановления.

## 2. Сервис скачивания из общей B2

Цель: загрузить файл через S2 и скачать через отдельный S3, читающий ту же файловую БД.

Остановка программы upload не означает остановку БД B2. Download работает независимо от процесса upload, напрямую читая общее хранилище. Копировать содержимое и подписываться ради этого на FileCreated не нужно.

Работы:
- Создать cmd/download с подключением к существующей B2 (upload_db).
- Добавить таблицу истории скачиваний в общей B2. Для общей БД вести одну согласованную последовательность миграций, не создавать files повторно из другого сервиса.
- Добавить GET /api/download/files/{id} через шлюз.
- Выдавать исходные байты как скачиваемое вложение с корректным именем, не исполнять загруженный HTML в браузере.
- Разрешить скачивание гостю. Действительный токен позволяет записать ID пользователя; отсутствие входа не отключает публичную выдачу.
- Записывать историю в B2: ID скачивания, ID файла, необязательный ID пользователя, время.
- Сохранять событие FileDownloaded через outbox вместе с записью истории.

Договорённость для подсчёта: считаем принятый запрос GET на выдачу существующего файла, а не доказанное сохранение на диске клиента. HEAD не увеличивает счётчик. Возобновление по Range пока не реализуем.

Признак готовности этапа: браузер загружает файл через upload и получает ту же последовательность байтов из download; после остановки процесса upload сохранённый файл продолжает скачиваться из общей B2.

После фиксации файла в B2 отдельной задержки репликации в download нет. Асинхронная задержка относится к обновлению каталога и статистики S4.

## 3. Каталог файлов

Цель: любой пользователь видит общий список из отдельной БД каталога B4, без прямого доступа каталога к файловой B2.

Работы:
- Создать cmd/catalog и catalog_db.
- Подписаться на события файлов, пользователей и скачиваний.
- Хранить готовые данные для чтения: файлы, владельцы, отображаемые имена, счётчики.
- Добавить GET /api/catalog/files и таблицу на странице.
- Выводить имя файла, владельца, ссылку скачивания и количество скачиваний.
- Добавить поиск по названию файла и имени владельца.
- Добавить сортировку по названию, имени владельца и количеству скачиваний.
- Добавить пагинацию, ограничение размера страницы и устойчивый дополнительный порядок по ID.
- Разрешить список и скачивание без входа.

Признак готовности этапа: загрузка и скачивание автоматически меняют данные каталога после обработки событий. Повторное событие не удваивает счётчик.

## 4. Удаление и изменение имени

Удаление:
- Добавить DELETE /api/upload/files/{id}.
- Разрешить удаление только владельцу, определённому по токену.
- Сохранить deleted_at и событие удаления одной транзакцией.
- Download проверяет deleted_at в общей B2 и прекращает выдачу удалённого файла; каталог убирает его после получения события.
- Учитывать версии и отметки удаления: запоздавшее старое событие создания не должно вернуть удалённый файл.

Изменение имени:
- Добавить PATCH /api/auth/me для DisplayName, не менять ID пользователя.
- Изменение пользователя и событие сохранить вместе в auth_db через outbox.
- Доставлять регистрацию и изменение имени в каталог.
- Обновлять имена владельцев в каталоге без синхронного вызова auth.

Существующие пользователи тоже должны появиться в локальном представлении каталога; запуск новой шины не должен требовать повторной регистрации.

Признак готовности этапа: изменения из интерфейса доходят до нужных сервисов автоматически, чужое удаление запрещено.

## 5. Статистика владельца

Цель: выполнить требование о количестве скачиваний и пользователях, которые скачивали файл.

Работы:
- Добавить GET /api/catalog/files/{id}/stats.
- Проверять право владельца по проверенному ID и локальным данным каталога.
- Показывать суммарное количество и историю скачиваний с пагинацией.
- Для зарегистрированных показывать отображаемые имена; для анонимных — «Гость», не придумывать их личность по IP.
- Историю связывать с user_id, а не считать имя постоянным идентификатором.

Признак готовности этапа: владелец видит статистику своего файла; другой пользователь и гость не получают чужой отчёт.

## 6. Завершить интерфейс и запуск проекта

Интерфейс:
- Свести регистрацию, вход, состояние сессии, каталог, загрузку, удаление, статистику и смену имени в понятный интерфейс.
- Показывать состояния ожидания, пустого списка, ошибки сервиса и истёкшего входа.
- Учесть задержку доставки событий: после действия не обещать мгновенного обновления всех сервисов.
- Затем оформить страницу аккуратно; не тратить основной этап на дизайн до появления нужных функций.

Запуск:
- Упаковать Go-сервисы в Docker, добавить недостающие БД и RabbitMQ в Compose.
- Вынести адреса в настройки: localhost внутри контейнера означает сам контейнер, поэтому межконтейнерные адреса нельзя оставить как при запуске Go с компьютера.
- Для обычного запуска оставить публичным только шлюз; отладочные порты БД/панелей ограничить локальной машиной либо отдельным профилем.
- Закрытый ключ доступен только авторизации; остальным сервисам достаточно публичного. Ключи не запекаем в образ и не коммитим.
- Сохранить независимые тома БД и брокера.
- Для публичного HTTPS отдельно настроить Secure-cookie и ожидаемый origin; текущая настройка HTTP — локальная учебная.

Признак готовности этапа: проект поднимается воспроизводимо, пользователь работает через один адрес шлюза.

## 7. Финальная проверка и материалы для защиты

Проверки по заданию:
- Остановить программу upload, не контейнер общей БД: остальные сервисы продолжают работу, сохранённые файлы доступны в download через B2.
- Остановить download: остальные функции не падают вместе с ним.
- Остановить catalog: остальные сервисы работают; файл по известному ID можно скачать.
- Остановить auth: гости по-прежнему видят каталог и скачивают файлы.
- Приостановить доставку только в catalog: старый список остаётся доступным; после возобновления данные автоматически догоняются.

Дополнительные проверки качества:
- Недоступный RabbitMQ, восстановление и отправка outbox.
- Повторные и запоздавшие события, отсутствие двойных счётчиков и воскрешения удалённых файлов.
- Границы размера и совпадение исходных байтов с файлом, скачанным из B2 через download.
- Права владельца, неправильный/истёкший токен, гостевые операции.
- Поиск, все варианты сортировки, переходы страниц.
- Перезапуск контейнеров без потери данных.

Материалы:
- README с понятным запуском и настройками.
- Схема сервисов и владения данными.
- Форматы событий и описание HTTP-маршрутов.
- Сценарий демонстрации с командами отключения и восстановления компонентов.
- Результаты действительно выполненных проверок, а не заранее написанные успешные отчёты.

## С чего продолжить

Начать с RabbitMQ, метаданных первого файлового события и outbox в общей B2 (upload_db). Ближайшие связанные цели:

- Сохранение: браузер → шлюз → upload → B2.
- Обновление списка: upload → outbox → RabbitMQ → catalog → B4.
- Скачивание: браузер → шлюз → download → чтение B2 → ответ через шлюз.

Не реализовывать отвергнутый вариант с копией файлов в download_db и передачей содержимого через RabbitMQ. Развивать рабочие пользовательские сценарии и доставку изменений в S4.
