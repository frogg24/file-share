# Вход и сохранение авторизации

## Текущая схема

1. Браузер отправляет JSON с логином и паролем в `POST /api/auth/login` через шлюз на порту 8080.
2. Шлюз пересылает запрос сервису авторизации на порту 8081.
3. Сервис проверяет пароль по хешу из PostgreSQL, создаёт JWT и записывает его в ответ через `Set-Cookie`.
4. Браузер хранит cookie `file_share_access` и автоматически отправляет её в последующих запросах к тому же хосту.
5. Шлюз извлекает JWT из cookie и проверяет подпись, срок, издателя, получателя и обязательные поля. Только после этого передаёт ID пользователя обработчику.
6. При загрузке страницы JavaScript вызывает `/api/me`. Поэтому после обновления страницы интерфейс восстанавливает состояние входа.

JWT больше не возвращается в JSON входа и не хранится в JavaScript, localStorage или sessionStorage. Формат JSON входа: `id`, `login`, `display_name`.

Старый способ `Authorization: Bearer ...` оставлен для API-клиентов и тестов. Явно переданный Authorization имеет приоритет; некорректный заголовок не заменяется автоматически cookie.

## Срок и выход

- JWT и cookie имеют срок 15 минут, заданный в `cmd/auth/main.go`.
- Cookie имеет положительный Max-Age и Expires: это не только временная переменная страницы.
- Обновление страницы не продлевает срок JWT.
- После истечения нужно войти снова. Refresh-токены пока не реализованы.
- Кнопка «Выйти» вызывает `POST /api/auth/logout`; сервер удаляет cookie с тем же именем и путём. Затем `/api/me` отвечает 401.
- Выход удаляет cookie браузера, но не отзывает отдельно скопированный JWT: такая копия криптографически действительна до истечения срока. Серверного списка отозванных токенов пока нет.

## Защита cookie

- HttpOnly: JavaScript не читает токен через document.cookie.
- SameSite=Strict, без Domain, Path=/.
- Локально используем обычный HTTP и Secure=false. Не использовать такую конфигурацию для публичного развёртывания.
- AUTH_COOKIE_SECURE=true включает флаг Secure для HTTPS. Само HTTPS этот параметр не настраивает.
- Шлюз дополнительно отклоняет изменяющие запросы с чужим Origin и запросы Sec-Fetch-Site: cross-site. CLI-запросы без браузерных заголовков поддерживаются.
- Если в будущем HTTPS завершает отдельный внешний прокси, потребуется отдельно настроить ожидаемый публичный origin; сейчас проверка использует схему и Host, полученные самим шлюзом.
- Ответы авторизации и защищённого маршрута помечаются Cache-Control: no-store.

## Файлы

- `internal/platform/session/cookie.go` — создание и удаление cookie.
- `internal/auth/handler.go` — установка cookie после входа и обработчик выхода.
- `internal/gateway/auth.go` — извлечение JWT из cookie или Bearer-заголовка, проверка и передача ID.
- `internal/gateway/origin.go` — проверка источника изменяющих запросов.
- `web/index.html` — автоматическая проверка входа при загрузке страницы и кнопка выхода.

## Проверка вручную

Перезапустить обе Go-программы, а не только обновить браузер:

```powershell
go run ./cmd/auth
```

В другом терминале:

```powershell
go run ./cmd/gateway
```

Открыть сайт шлюза на localhost, порт 8080, выполнить Ctrl+F5.

1. Войти существующим пользователем.
2. Обновить страницу — ID остаётся виден без повторного ввода пароля.
3. Нажать «Выйти» — вход сбрасывается.
4. Обновить страницу — пользователь остаётся неавторизованным.

Хост должен оставаться тем же: cookie localhost и cookie 127.0.0.1 — разные.

## Автоматическая проверка

```powershell
go test ./...
go vet ./...
go build ./...
```

`cmd/gateway/session_integration_test.go` запускается с тегом integration и существующим тестовым аккаунтом, заданным через FILE_SHARE_TEST_LOGIN и FILE_SHARE_TEST_PASSWORD. Он читает настоящую БД, но не создаёт и не удаляет пользователей, не изменяет пароли и не использует постоянные ключи разработчика. HTTP-серверы и ключи этого теста временные. Обычные тесты не требуют БД.
